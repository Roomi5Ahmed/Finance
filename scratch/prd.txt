1. Overview
1.1 Project Summary
The Smart Finance Tracker is a cross-platform personal finance application that connects to payment services and bank accounts to automatically track expenses, presents visualised weekly/monthly/yearly spending dashboards, and proactively suggests cheaper alternatives to the user's current subscriptions and software — for example, recommending DaVinci Resolve as a free alternative to Adobe Premiere Pro.
The product ships first as a web application (Next.js), then is converted to a React Native mobile app (Expo) in Month 4, sharing business logic through a shared monorepo package.
1.2 Sprint Scope — Weeks 1–2
This sprint covers the entire project foundation. No end-user-visible features ship in this sprint; the deliverable is a deployed skeleton application that subsequent sprints can build upon confidently.

In scope: Repo setup, CI/CD, database schema design, Prisma ORM setup, NextAuth.js authentication (Google + email/password), base layout shell, onboarding flow wireframes, and reusable component library.

Out of scope: Transaction entry, Plaid integration, dashboards, suggestion engine, mobile app — all deferred to Weeks 3–16.
1.3 Success Definition
The sprint is complete when all of the following are true:
A Next.js 14 app is live on Vercel at a public URL with zero build errors.
A PostgreSQL database is provisioned on Supabase (free tier) with all schema tables migrated.
A user can sign in with Google OAuth and email/password, and their session persists across page refreshes.
The dashboard shell renders (empty state) with sidebar navigation and responsive layout.
The onboarding modal launches for new users and stores currency preference + income in the database.
GitHub Actions CI runs on every pull request: lint, type-check, and Prisma schema validation all pass.
Figma wireframes are complete for Dashboard, Transaction List, Add Expense, and Settings screens.

3. Functional Requirements
3.1 Authentication System
3.1.1 Google OAuth
Implement NextAuth.js with the Google provider using NEXTAUTH_SECRET and GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET environment variables.
On first OAuth sign-in, create a User record in the database with name, email, image, and provider set to 'google'.
Redirect to /onboarding after first sign-in; redirect to /dashboard on subsequent sign-ins.
Session token is stored as a secure, httpOnly cookie with a 30-day max-age.
3.1.2 Email/Password Authentication
Implement NextAuth.js Credentials provider with bcrypt password hashing (salt rounds: 12).
Registration form must validate: email format, password minimum 8 characters, one uppercase, one number.
Display inline field-level error messages on validation failure without clearing the form.
Rate-limit login attempts to 5 per minute per IP using a middleware edge function.
3.1.3 Password Reset
Generate a signed JWT reset token valid for 1 hour, stored in PasswordResetToken table.
Send reset email via Resend API (free tier: 3,000 emails/month).
Token is invalidated after use or expiry — single-use only.
3.2 Onboarding Flow
Onboarding modal renders as a multi-step flow: Step 1 — Currency & locale, Step 2 — Monthly income (optional), Step 3 — Primary goal (Save money / Reduce subscriptions / Track spending / Debt paydown).
Currency selector searches from a list of 50 common currencies with ISO codes.
All onboarding data is saved to the UserProfile table on completion of the final step.
A onboardingCompleted boolean on the User record gates whether the modal appears on login.
'Skip for now' sets onboardingCompleted = false and stores nothing — the modal re-appears on next login.
3.3 Base Layout
App shell uses Next.js App Router layout.tsx with a persistent sidebar and a main content slot.
Sidebar items: Dashboard (icon: BarChart2), Transactions (Receipt), Insights (Lightbulb), Budgets (Target), Accounts (Building2), Settings (Settings). Each links to /dashboard, /transactions, /insights, /budgets, /accounts, /settings respectively.
Active route is highlighted with a brand-colour left border and a tinted background.
Sidebar is 240px wide on desktop; collapses to 0px with an animated slide-out on mobile (<768px).
Top header bar shows: user avatar + name (right), page title (left), and a notification bell icon.
All pages that require authentication redirect to /auth/signin if the session is null — handled in middleware.ts.
3.4 Component Library
The following components must be built as standalone, Storybook-documented (optional) primitives in /components/ui/:
Button — variants: primary, secondary, ghost, destructive. Sizes: sm, md, lg. Loading spinner state.
Card — with optional header, body, and footer slots. Hover elevation variant.
Modal — accessible dialog with focus trap, Escape to dismiss, backdrop click to dismiss.
Input — text, email, password (with show/hide toggle), number. Error and helper text slots.
Select — searchable dropdown built on Radix UI primitives.
Badge — colour variants: green (income), red (expense), blue (transfer), gray (neutral).
Skeleton — animated loading placeholder that matches the shape of the content it replaces.
Avatar — circular image with fallback initials. Sizes: sm (24px), md (36px), lg (48px).
Toast — success, error, warning, info variants. Auto-dismiss after 4 seconds. Stacked queue.

5.3 Environment Variables
All secrets are stored in .env.local (gitignored) and configured in Vercel project settings. The following must be set before the app will start:

DATABASE_URL=postgresql://...               # Supabase connection string
DIRECT_URL=postgresql://...                # Direct URL (required by Prisma for migrations)
NEXTAUTH_URL=https://your-app.vercel.app   # App base URL
NEXTAUTH_SECRET=<random 32-char string>    # Session signing secret
GOOGLE_CLIENT_ID=<from Google Console>
GOOGLE_CLIENT_SECRET=<from Google Console>
RESEND_API_KEY=re_<from Resend dashboard>
5.4 CI/CD Pipeline
GitHub Actions runs the following pipeline on every push to main and on every pull request:
Checkout code and install dependencies (pnpm install --frozen-lockfile).
Run ESLint (pnpm lint) — fails on any error, warns on warnings.
Run TypeScript type-check (pnpm tsc --noEmit) — zero type errors allowed.
Validate Prisma schema (pnpm prisma validate).
Run unit tests (pnpm test) — must all pass.
Vercel automatically deploys preview URLs on PR; promotes to production on merge to main.

6. Non-Functional Requirements
6.1 Performance
Largest Contentful Paint (LCP) must be under 2.5 seconds on a simulated 4G connection.
Time to First Byte (TTFB) must be under 800ms for all server-rendered pages.
All database queries in this sprint must complete in under 100ms (schema is small; no optimisation needed yet).
6.2 Security
All pages under /(dashboard) must be protected by auth middleware — unauthenticated requests redirect to /auth/signin with a callbackUrl parameter.
Passwords are hashed with bcrypt (cost factor 12) and are never logged or returned in API responses.
OAuth tokens are encrypted at rest in the database using the NEXTAUTH_SECRET as the encryption key.
CSP headers are set via next.config.js: default-src 'self'; script-src 'self' 'nonce-{nonce}'.
Rate limiting: 5 login attempts per minute per IP. Implemented as an Edge Middleware function.
6.3 Accessibility
All interactive elements must be keyboard-navigable and have visible focus indicators.
Form fields must have associated <label> elements. Error messages linked via aria-describedby.
Modal dialogs must trap focus and return focus to the trigger on close.
Colour contrast ratio for all body text must meet WCAG 2.1 AA (4.5:1 minimum).
6.4 Code Quality
ESLint with eslint-config-next + @typescript-eslint/recommended. Zero errors on CI.
Prettier for formatting. Enforced via a pre-commit hook (husky + lint-staged).
Each component and utility function must have a JSDoc comment explaining its purpose.
No any type in TypeScript — use unknown or proper typed interfaces.

8. Acceptance Criteria
Each user story below must pass its acceptance criteria before being marked Done. Criteria are written as given/when/then scenarios.
US-01 — Google Sign-In
Given a new visitor on /auth/signin, when they click 'Continue with Google' and authenticate successfully, then they are redirected to /onboarding and a User record is created in the database.
Given a returning user, when they sign in with Google, then they are redirected to /dashboard (not /onboarding).
Given a user who cancels the Google OAuth dialog, when they return to the app, then they remain on /auth/signin with no error shown.
US-02 — Email/Password Registration
Given a registration form, when submitted with a valid email and password meeting all requirements, then a User is created, the password is stored as a bcrypt hash, and the user is redirected to /onboarding.
Given a registration form, when submitted with an email already in use, then an inline error 'An account with this email already exists' is shown.
Given a registration form, when submitted with a password shorter than 8 characters, then an inline error 'Password must be at least 8 characters' is shown and no record is created.
US-06 — Onboarding Modal
Given a new user on their first login, when /dashboard loads, then the onboarding modal renders immediately over the dashboard shell.
Given a user on onboarding Step 1, when they select 'INR — Indian Rupee' and click Next, then Step 2 is shown and the currency is staged in local state.
Given a user who completes all 3 steps, when they click 'Get Started', then UserProfile is created in the database, onboardingCompleted is set to true, and the modal closes.
Given a user who clicks 'Skip for now', when they next log in, then the modal appears again.
US-09 — Navigation
Given a signed-in user on /dashboard, when they click 'Transactions' in the sidebar, then the URL changes to /transactions and the Transactions link is highlighted.
Given an unauthenticated user who navigates directly to /dashboard, when the page loads, then they are redirected to /auth/signin?callbackUrl=%2Fdashboard.
